## 2026-09-06 — Engine facts verified against OpenSpiel 2.0.2

**Context.** Before writing any code, the gin rummy API was probed directly
rather than recalled, because getting the action layout or tensor semantics
wrong is expensive and silent.

**Finding.** `gin_rummy` has 241 actions (`0–51` discard, `52` draw upcard,
`53` draw stock, `54` pass, `55` knock, `56–240` meld declarations), a 644-dim
observation tensor, `max_game_length` 300, utility range ±123, and defaults
`gin_bonus=25 undercut_bonus=25 knock_card=10 hand_size=10 num_ranks=13
num_suits=4 oklahoma=False`.

**Consequence.** Recorded in `src/ginrl/spiel_facts.py`, generated by
`scripts/probe_env.py`. All code imports from there. `make facts-check` fails
the build on drift.

## 2026-09-06 — No information-state tensor; observation is not Markov

**Context.** Looking for the tensor to feed the network.

**Finding.** `information_state_tensor()` raises
`InformationStateTensorShape unimplemented`. Only `observation_tensor()` exists,
and a single observation does not record which cards the opponent drew from the
discard pile or which upcards they declined — the two main inference channels in
this game. Separately, of the 644 dims, roughly 390 are identically zero
throughout normal play (they encode laid melds, populated only after a knock).

**Consequence.** We do not consume the raw tensor. Features are built from
`state.to_observation_struct(p).to_dict()` plus a per-seat `BeliefTracker` that
accumulates history. See METHODOLOGY.md §4. A bit-exact information-hygiene test
using `resample_from_infostate` guards against leaking the hidden hand into
features.

## 2026-09-06 — `GinRummyUtils` exists; do not write a meld solver

**Context.** Assumed we would need our own deadwood/meld-search code.

**Finding.** `pyspiel.gin_rummy.GinRummyUtils(num_ranks, num_suits, hand_size)`

an ablation in Phase 6, not an assumption.

## 2026-09-06 — `SimpleGinRummyBot` calling protocol

**Context.** The reference opponent crashed with a C++ `CHECK_TRUE` failure on
`legal_actions` during the second game.

**Finding.** The bot is stateful. `restart_at(state)` raises
`RestartAt(state) not implemented`. Reusing a bot instance across games leaves
stale internal state and produces illegal actions. It also needs
`inform_action(state, player, action)` for every action it did not take,
including chance outcomes.

**Consequence.** `ginrl/agents/simple_spiel_bot.SimpleBotRunner` constructs a
fresh pair per game and informs both bots of every action. With that,
`pyspiel.evaluate_bots` and a manual loop both work. Self-play reference numbers:
≈34 decisions/game, ≈16.4 points/hand mean absolute score, no wall endings.

## 2026-09-06 — Exact exploitability is infeasible for gin rummy at every size

**Context.** Planned to use a reduced deck with exact `nash_conv` as ground truth.

**Finding.** Reduced decks do work — `num_ranks`, `num_suits` and `hand_size`
genuinely shrink the deck and hands (subject to
`num_ranks*num_suits >= 2*hand_size + WALL_STOCK_SIZE + 1`, with
`WALL_STOCK_SIZE == 2`), though the action and observation spaces stay padded at
241/644. But `exploitability.nash_conv` was killed by the OOM reaper even on the
smallest legal configuration.

**Consequence.** Exact exploitability is used only on Kuhn and Leduc, to validate
the trainer in Phase 3 (anchors: uniform random NashConv 0.9167 and 4.7472
respectively). For gin rummy we use RL best response and ISMCTS-BR, which give
lower bounds. Phase 4 keeps a 45-minute timeboxed spike to confirm, then stops.

## 2026-09-06 — α-Rank numerics

**Context.** First run of `alpharank.compute(tables, alpha=1e2)`.

**Finding.** Emits `RuntimeWarning: overflow encountered in exp` from the Fermi
selection term at realistic payoff scales.

**Consequence.** Use `use_inf_alpha=True` with `inf_alpha_eps`, or sweep α with
`sweep_pi_vs_alpha` and report the plateau. `configs/gates.yaml` requires the
tournament to run warning-free. Also recorded: α-Rank is not clone-invariant, so
Phase 6 reports a leave-one-out stability check and a bootstrap over the
estimated payoff matrix.

## 2026-09-06 — Algorithm family chosen: regularised policy gradient, not CFR

**Context.** Choosing between Deep CFR / DREAM / ESCHER, NFSP, PSRO, R-NaD, MMD,
and plain PPO.

**Decision.** One trainer implementing mirror descent with a magnet term, with
the magnet configurable as uniform (≡ PPO with entropy bonus), a periodic
snapshot (≡ MMD), or an EMA of the learner. Annealed regularisation, linear and
power-law schedules.

**Rationale.** R-NaD/DeepNash showed regularised self-play scales to games far
larger than gin rummy without search; MMD proved linear convergence to QREs in
extensive-form games and later reached superhuman Stratego with annealed
schedules; and a 5 600-run controlled comparison found NFSP, PSRO, ESCHER and
R-NaD failed to outperform generic regularised policy gradient. Porting R-NaD
from JAX to run on Apple Silicon is cost without expected benefit.

**Consequence.** No JAX, no TensorFlow, no CFR implementation in this repo. NFSP
is optional as a sanity baseline only.

## 2026-09-06 — Telemetry: Trackio primary, TensorBoard secondary, JSONL underneath

**PARTLY SUPERSEDED.** TensorBoard was later dropped — `trackio.Histogram`
exists, so there was no capability gap, and the `TrackioSink` had been degrading
histograms to three scalars to work around a limitation that does not exist.
`make board-tb` does not exist. Everything else in this entry stands: Trackio
primary, JSONL as the source of truth, failure-isolated optional sinks. See
`docs/OBSERVABILITY.md`, "Why not TensorBoard as well".

**Context.** Requirement for live observability of training, "TensorBoard or the
newest equivalent".

**Finding.** Trackio (Hugging Face, v0.37 on PyPI, pure Python so fine on 3.13)
is local-first with no account, stores runs in SQLite, is API-compatible with
`wandb.init/log/finish`, and ships a CLI including `trackio list`, `trackio get`
and `trackio query --sql`. Verified working headlessly. Its `metrics` column in
SQLite is a hex-encoded JSON blob, so raw SQL needs decoding — `trackio get` is
the readable path.

**Decision.** Trackio is the primary dashboard, chosen mainly because a coding
agent can interrogate its own run through the CLI rather than needing a human to
read a chart. TensorBoard is kept as a second sink for histogram and distribution
views. Both sit behind `ginrl.telemetry.recorder.Recorder`.

**Consequence.** `runs/<run>/metrics.jsonl` is the source of truth; gates and
`docs/RESULTS.md` read only that. Optional sinks are failure-isolated: a dead
dashboard warns and the run continues. `make board`, `make board-tb`, `make elo`.

## 2026-09-06 — Elo is unsafe here without a transitivity diagnostic

**Context.** Wanted a single "is it improving" scalar to watch during training.

**Finding.** Elo is a one-dimensional model and assumes transitivity. Verified in
a unit test: on an exact rock-paper-scissors population, the Bradley-Terry fit
returns three ratings within two points of each other — Elo cannot represent the
cycle at all. A self-play league against past checkpoints could therefore show a
smoothly rising Elo while the agent cycles. Gin rummy styles (gin-seeking versus
early-knocking versus balanced) are a plausible source of exactly this.

**Decision.** Ratings come from `ginrl.eval.ratings.fit_ratings`: anchored
Bradley-Terry MLE refit over the whole game record (checkpoints are frozen, so a
static fit is the correct estimator, not incremental Elo), `SimpleGinRummyBot`
pinned at 0, L2 prior for identifiability, CIs from the observed information
matrix, mirrored duplicate deals collapsed into paired observations, and a
first-player-edge term as a free check that the harness really mirrors.
`ratings/cyclic_fraction` — the Helmholtz-Hodge residual share — is logged beside
every Elo and is a tripwire.

**Verified in tests.** Recovers known Elos to within 5 points over 30k games;
RPS reads cyclic_fraction 1.0 and a transitive ladder 0.0006; an undefeated agent
gets a finite rating; a 4 point/hand edge buried in ±30 points of deal variance
shows as 55% raw win rate and 100% paired; a synthetic 52-Elo seat advantage is
recovered as 54.

**Consequence.** No incremental Elo loop anywhere. `runs/game_record.jsonl` is
append-only and every rating is reproducible from disk. A rising Elo with a
cyclic fraction above 0.25 fails the Phase 5 gate.

## 2026-09-06 — Headline progress metric is points/hand, not Elo

**Context.** Challenged on why the rating code fits Bradley-Terry rather than
using ordinary Elo for what is, after all, a 1v1 game.

**Clarification.** Logistic Elo *is* Bradley-Terry; `fit_ratings` produces
ordinary Elo on the ordinary scale. The difference is estimation: classic Elo is
online SGD on the BT likelihood with step size K, this is batch MLE. Measured on
3,000 synthetic games with known ratings — reshuffling game order alone moves
online Elo (K=32) by up to 290 points per agent while the batch fit is
bit-identical; K from 8 to 64 moves one agent from +15 to −119; RMSE vs truth is
101 Elo online against 38 batch. K is a tracking parameter for drifting human
strength, and our checkpoints are frozen, so there is nothing to track.

**Decision, and the concession.** The challenge was right that a rating system
is overkill for the training curve. The headline progress metric is now
`ratings/points_per_hand_vs_anchor` — mean paired score per hand against
`SimpleGinRummyBot`, with a CI. Model-free, in game units, no anchor convention,
no K. Elo is demoted to a pool-level statistic: it earns its place only when
twenty checkpoints, a heuristic family and an ISMCTS baseline have not all played
each other and a single comparable scale is needed. `cyclic_fraction` still
governs whether that scale means anything.

## 2026-09-06 — Nash averaging is the population ranking; α-Rank is a second lens

**Context.** α-Rank was specified up front. Challenged on whether it survives the
same scrutiny applied to Elo.

**Finding.** Largely it does not, for *this* meta-game. α-Rank exists for
n-player general-sum games where Nash is PPAD-complete. Ours is two-player,
symmetric and zero-sum: the payoff matrix is antisymmetric, Nash is a linear
program over a ~16×16 matrix, and Nash averaging is clone invariant in exactly
this setting. We would be surrendering invariance to dodge an intractability we
do not have.

Measured on a synthetic style meta-game with an intransitive cycle
(`gin_seeker > patient_knock > fast_knock > gin_seeker`, plus a balanced player),
cloning `fast_knock` into four near-identical seeds:

| | gin_seeker | patient_knock | fast_knock family |
|---|---|---|---|
| max-ent Nash before → after | 0.417 → 0.417 | 0.333 → 0.333 | 0.250 → 0.250 |
| α-Rank before → after | 0.332 → 0.110 | 0.332 → 0.435 | 0.332 → 0.454 |

The Phase 6 population is near-clones by construction — five `gin_seeker(λ)`,
several `knock_rusher(κ)`, five `heuristic(T)` — so under α-Rank the winning
style would partly reflect which family was swept most finely. Second issue: the
cycle has unequal weights (3, 5, 4); Nash returns 0.417/0.333/0.250 while α-Rank
at high α returns 0.332/0.332/0.332, because it reads only the sign of each
matchup from the response graph. In gin rummy the margin is the payoff.

**Decision.** `ginrl.eval.population.nash_averaging` — maximum-entropy Nash — is
the headline population ranking. Maximum entropy specifically, not any Nash: it
is what splits duplicated strategies evenly and delivers the invariance.
α-Rank is retained and reported because it answers a different and legitimately
interesting question — which styles persist under evolutionary selection, which
is a fair reading of "would early knockers take over a population of
gin-chasers" — but always with `clone_invariance_error` reported beside it, and
never as the ranking.

**Note.** `open_spiel.python.algorithms.lp_solver` requires `cvxpy`, and in any
case returns *a* Nash rather than the maximum-entropy one, so it does not give
clone invariance. We use our own scipy SLSQP solve and avoid the dependency.

**Verified in tests.** Nash drift under cloning 0.0000 vs α-Rank 0.2225;
transitive ladder puts mass 1.0 on the best; exact RPS returns uniform.

## 2026-09-06 — Correction: rank by A·p, not by Nash mass

**Context.** Asked directly whether we are using Balduzzi's Nash averaging. We
are — the agent-vs-agent variant of *Re-evaluating Evaluation* (NeurIPS 2018) —
but checking the definition exposed an error in the first implementation.

**Error.** `nash_averaging` returned the equilibrium mass `p` and called it the
ranking. Balduzzi's rating is the payoff against the maximum-entropy Nash
mixture, `A @ p`, which is equivalent to ranking by Nash-equilibrium regret. The
mass is the meta-strategy weighting, not a strength estimate.

**Why it matters.** On a transitive ladder A > B > C > D, the mass is
`{1.0, 0, 0, 0}` — no ordering at all below the top — while `A @ p` is
`{0, −2, −5, −9}` and orders correctly. Our own transitive-ladder unit test had
shown this and it was misread as a pass.

**Fix.** `PopulationRanking` now carries `nash_average` (rank by this) and
`nash_mass` (report as support, plus a `.support` property). Both are clone
invariant — measured drift 0.000000 against α-Rank's 0.2225.

**Consequence for the write-up.** Every supported strategy scores 0 by
construction, so Nash averaging returns a *set* of maximally general styles
rather than a winner. The honest Phase 6 headline may be "gin_seeker,
patient_knock and fast_knock are jointly unseparable, and balanced loses 1
point/hand to their mixture" rather than a single ranking. That is the correct
answer to a cyclic question, and the reason the mass is still reported: it says
how much weight each style carries inside that set.

**Also noted.** Clone invariance of max-entropy Nash is established for
two-player zero-sum and is known to fail in n-player general-sum — further
confirmation that our symmetric zero-sum meta-game is the right home for this
method. A newer alternative, deviation ratings (arXiv 2502.11645), claims clone
invariance in general settings; not adopted, but worth revisiting if the
population ever stops being two-player zero-sum.

## 2026-09-06 — mElo added; it is not the same thing as Nash averaging

**Context.** Asked whether what we are doing could also be called
multidimensional Elo.

**Answer: no, but the question surfaced a gap worth filling.** mElo and Nash
averaging are separate contributions of the same paper (Balduzzi et al. 2018):
mElo is section 3, a *predictive* model that can express cyclic outcomes; Nash
averaging is section 4, an *evaluation* method whose selling point is clone
invariance. They are not interchangeable and we now use both.

**Where it slots in.** Under the Hodge decomposition `A = grad(r) + rot(A)`,
ordinary Elo models only `grad(r)`. Our `fit_ratings` is therefore already mElo
with k = 0, and `cyclic_fraction` measures the size of the residual that mElo
models. Adding `fit_melo` closes the loop: instead of only reporting that a
cycle exists, we get its shape.

**Why it is worth the code for this project specifically.** With k = 1 the
cyclic term is the 2D cross product of the embeddings, so cycling agents sit at
successive angles around a circle — a **style wheel** showing the axes along
which gin-seeking, patient knocking and fast knocking beat one another. That is
a direct answer to the original question rather than a proxy for it.

**Verified in tests.** Rock-paper-scissors: Elo log-loss 0.6930 (coin flip) vs
mElo₂ 0.0980, 85.9% explained, strategies 120° apart. Transitive ladder: 0.0%
explained, cyclic strength 0.000, ratings identical to plain Bradley-Terry — it
degrades gracefully instead of fitting noise. Mixed style meta-game: 22.8%
explained, specialists at |c| ≈ 1.4 around the wheel, balanced player at 0.13
near the origin.

**Two implementation notes.** The fit is non-convex in `C`, unlike plain
Bradley-Terry, so `fit_melo` uses several restarts and keeps the best
likelihood. And `||C||` is meaningless — the embedding is identified only up to
rotation and parallel vectors contribute nothing — so `cyclic_strength` (the
largest cyclic logit between any pair) is the reported quantity.

**Bug found while adding this.** The first version applied the L2 prior to the
un-centred rating vector and then anchored afterwards, which fought the anchor
and mis-ordered a transitive ladder (B rated above A). The prior is now applied
to the centred vector, since the likelihood depends only on rating differences.
The regression test is that mElo's ratings must match the plain Bradley-Terry
fit on transitive data.

## 2026-09-06 — alpha-Rank is not multidimensional; Schur spectrum added

**Context.** Asked whether alpha-Rank has multidimensional properties like mElo.

**Answer: no.** alpha-Rank returns one scalar per strategy, the stationary mass.
It is cycle-*aware* — on rock-paper-scissors it correctly returns 1/3, 1/3, 1/3
rather than forcing an order — but not cycle-*descriptive*: those numbers say
nothing about the cycle's structure, where mElo places the three strategies 120
degrees apart. Its richer intermediate objects (Markov transition matrix,
response graph) are the n x n data re-expressed, not a learned low-dimensional
embedding, and the alpha sweep is a one-parameter family, not a second
dimension. mElo is the only tool here that gives each agent a vector.

**Dimensionality of each tool, for the record.**

| method | output per agent | cycle-aware | cycle-descriptive |
|---|---|---|---|
| Elo / Bradley-Terry | scalar + CI | no | no |
| mElo_2k | scalar + 2k-vector | yes | yes (geometry) |
| Nash averaging | scalar (A·p) + mass | yes (declines to order) | no |
| alpha-Rank | scalar (stationary mass) | yes (spreads mass) | no |
| cyclic_fraction | one scalar for the pool | — | magnitude only |

**Gap this exposed, now filled.** k was being hardcoded to 1. Added
`schur_spectrum`, which splits the pairwise structure into a transitive axis and
ranked cyclic planes — a real antisymmetric matrix has eigenvalues in conjugate
pairs, one pair per plane — and suggests k from the data. `configs/gates.yaml`
now requires k to come from the spectrum rather than being set by hand.

**Verified.** Rock-paper-scissors: 99.9% cyclic, one plane, k=1. Transitive
ladder: 99.9% transitive, k=0. Two independent 3-cycles: two planes at
0.53/0.47, k=2. Transitive spine plus one style cycle among mid-strength peers:
89.9% transitive, one plane carrying 99% of the rest, k=1.

**Bug found while adding this.** The first version took the top m/2 eigenvalue
magnitudes, but each cyclic plane contributes a *conjugate pair*, so one plane
was counted twice — two independent cycles reported as three planes of
comparable size. Now strides by two after sorting. The regression test is that
two disjoint 3-cycles must return exactly two planes.

**New testable prediction adopted.** Czarnecki et al. (2020) argue real games
look like spinning tops: a dominant transitive axis with cyclic dimensions
widest at intermediate skill, narrowing toward equilibrium. Phase 6 now compares
`cyclic_energy` over mid-training checkpoints against near-champion checkpoints.
If the prediction holds, style choice matters in the middle and washes out at
the top, which is a more interesting answer to the original question than either
style simply winning.

## 2026-09-06 — Evaluation stack trimmed and tiered

**Context.** Challenged that mElo plus Nash averaging plus alpha-Rank is
overkill. It was. Worth recording *how* it happened: each of the previous four
turns answered a question by adding a tool, and none asked what the new tool
displaced. That is the normal way an evaluation stack rots, and it is a failure
mode a coding agent will repeat.

**Redundancy found.** `cyclic_fraction` and `schur_spectrum` computed the same
Helmholtz-Hodge decomposition in two places — literal duplicate code, 41 lines.
`cyclic_fraction` now delegates; behaviour verified unchanged (RPS 0.9994,
transitive ladder 0.0006). Separately, `fit_ratings` and `fit_melo` are one
model family, not two: Bradley-Terry is mElo with k=0. The convex k=0 path is
kept as a separate function only because the closed-form confidence intervals
are clean there and not in the non-convex k>0 case.

**Tiering adopted.** Tier 1, gated: points/hand vs anchor, Elo with CI,
`cyclic_fraction`, Nash averaging, RL-BR. Tier 2, one figure for the write-up
and not gated: `schur_spectrum` + `fit_melo`, which are a single unit — the
spectrum picks k, mElo draws the style wheel. Tier 3, off by default:
alpha-Rank.

**alpha-Rank demoted rather than deleted.** It was specified at the outset and
stays reachable via `scripts/tournament.py --alpha-rank`, but it is out of the
pipeline and out of every gate. It is not clone invariant, which is
disqualifying for a population built from parameter sweeps; at high alpha it
reads only the sign of each matchup and discards the margin, which in gin rummy
is the payoff; and the evolutionary question it answers is largely covered by
the Nash averaging support set, clone-invariantly.

**Guard added to CLAUDE.md.** Adding an evaluation metric now requires naming
which one it replaces or demotes, in the same ADR entry.

## 2026-09-06 — /loop scoped to phases 0-3, with a mechanical guard

**SUPERSEDED by the entry below.** The claim that `/loop` is not a built-in
command was wrong, and the primitive described here is `/goal`. The scope
argument and the guard survive; the mechanism did not.

**Context.** Request for a `/loop` command to work the plan autonomously.

**Note first.** `/loop` is not a built-in Claude Code command. Custom commands
are markdown files in `.claude/commands/`, so this needed `.claude/commands/loop.md`
(the command) plus `LOOP.md` (the protocol it enforces, kept at root so it is
reviewable and version-controlled like the other contracts).

**Decision: loop phases 0-3, stop there.** A loop optimises for one thing —
making the gate exit 0 — which is safe exactly when the gate is anchored to
something the agent cannot move. Phases 0-3 are: the engine reports its own
scoring, our deadwood must agree with it, information hygiene is bit-exact under
`resample_from_infostate`, and Kuhn/Leduc exploitability is exactly computable
with anchors 0.9167 and 4.7472 that are facts about those games. Looping there is
persistence.

From Phase 4 the gates still hold uncalibrated `TODO` thresholds. A loop pointed
at a TODO fills it with whatever its own run cleared — compliant with the
append-only rule and worthless. Phases 4-5 also exceed the 30-minute
stop-and-ask limit, and 6-7 ask interpretive questions where the honest answer
may be "these three styles are unseparable" and a loop will always produce *an*
answer.

**Guard added.** `make loop-guard` hashes `configs/gates.yaml`, the `Makefile`
and `tests/`, and fails on any change; `make loop-reset` re-baselines after a
reviewed edit. It also refuses to baseline when those files differ from `HEAD`,
which closes the hole where a tampered tree becomes the baseline. Verified
across four cases: clean tree passes, tampering after baselining fails,
tampering before baselining fails, restoration passes. Degrades safely outside
a git repo and before the first commit.

**Incident while testing, worth recording.** A `git add -A` during testing
committed a tampered threshold, which made it HEAD, after which the guard
correctly reported no drift. The guard was right and the test was wrong — but it
is exactly the failure mode the guard exists to prevent, arriving through the
commit rather than the edit. `make status` prints the `gates.yaml` hash for this
reason; compare it against the value in the phase's ADR entry, not just against
the working tree.

## 2026-09-06 — Correction: /loop is built in, and it is not the primitive we wanted

**Context.** The previous entry asserted that `/loop` is not a built-in Claude
Code command and shipped `.claude/commands/loop.md` as a custom one. A user
correction ("I am using it right now in another session") prompted a proper
check. The assertion was wrong, and it was wrong through bad reasoning: a search
for *custom* slash commands returned no mention of `/loop`, and absence of
evidence was treated as evidence of absence. `/loop` postdates the training
cutoff.

**What `/loop` actually is.** A time-driven repeat: the next turn starts when a
timer fires, not when a check passes. Fixed interval (`/loop 15m ...`) or
self-paced (Claude picks a 1m-1h delay). Bare `/loop` reads **`.claude/loop.md`**
(project) or `~/.claude/loop.md` (user); explicit prompts on the command line
ignore that file. Session-scoped: 50 tasks, 7-day expiry, 1-minute minimum,
fires only when Claude is idle with no catch-up for missed fires. Sub-hourly
tasks jitter up to half the interval late. Esc cancels the next wakeup;
`CLAUDE_CODE_DISABLE_CRON=1` disables scheduling.

**Three errors, one of which changed the design.**

1. *Wrong file.* `.claude/commands/loop.md` creates a custom command that would
   shadow the built-in. Deleted. The customisation point is `.claude/loop.md`.
2. *Wrong primitive.* "Iterate until the gate passes" is `/goal`, which is
   completion-driven and implemented as a session-scoped Stop hook: after each
   turn the condition and transcript go to a small fast model returning yes/no.
   The scope argument from the previous entry was right; it just belongs to
   `/goal`.
3. *Wrong recommendation.* Having mislabelled the primitive, the previous entry
   dismissed automation for Phase 5. In fact `/loop` is well suited there — you
   do not loop the training, you loop the *watching* of it. `.claude/loop.md`
   now holds a read-only watch prompt: tail `runs/<run>/metrics.jsonl`, compare
   against `tripwires:` in `configs/gates.yaml`, report two lines, stop on a
   fire.

**New constraint discovered.** Scheduled tasks fire only when Claude is idle and
missed fires are not caught up, so a foreground training run blocks every
wakeup. Long runs must be backgrounded and observed through the JSONL — which is
another argument for the JSONL being the source of truth rather than a dashboard.

**Limitation of `/goal` worth knowing.** Its evaluator reads the transcript and
does not run commands, so it can be satisfied by a transcript that merely claims
a gate passed. The gate must actually be run with its output in the transcript,
and `make loop-guard` remains the thing that blocks the cheaper path of editing
the gate.

**Unverified.** Some sources give the introduction version as v2.1.71 and a

## 2026-09-07 — The unit of play is the match, not the hand

**Context.** The project's question is "knock early, hold for gin, or balance".
Asked at the level of a single hand, it has a single answer. Asked at the level
of a match, it has a *surface*, because the optimal knock threshold moves with
the score.

**Finding.** OpenSpiel's `gin_rummy` is one hand. Real gin rummy, the North
American rules OpenSpiel's defaults implement, and the EAAI Gin Rummy
Undergraduate Research Challenge — the field's standing benchmark, run by
Gettysburg — all play successive hands to 100. EAAI's parameters match
OpenSpiel's exactly: gin bonus 25, undercut bonus 25, knock at 10, and a hand
replayed when the stock reaches two cards (which is `WALL_STOCK_SIZE == 2`,
independently confirming landmine 4). So the single-hand framing was not a
simplification of the standard setting; it was a different setting.

**Decision.** `ginrl/env/match.py` wraps the engine: hands to a target score
(default 100), the **match is the episode**, hand scores are intermediate
rewards, and own score / opponent score / differential / points-to-target are
features. Phases 3-4 stay hand-level because runs there are minutes and the
point is fast feedback. Phase 5 onward trains and evaluates on matches.

**Consequence.** Duplicate deals extend to duplicate *matches*, same seed
sequence with seats swapped. Both levels are always reported: points per hand is
the low-variance training signal, match win rate is the objective. `gate-p5`
gains a match win rate with a CI and — the substantive one — a requirement that
mean deadwood at knock differ CI-separably between the extreme score buckets. A
policy that knocks identically at +90 and −90 is a hand-level agent in a
match-level wrapper, and that failure is otherwise invisible. `style/*_by_score/`
metrics are added; METHODOLOGY §6.1 states the three falsifiable hypotheses.

**Watch for.** A match is a correlated sequence of hands. It must not be fed to
the Bradley-Terry fit as though its hands were independent observations —
ratings continue to be fit from paired hands.

## 2026-09-07 — Architecture is an experimental dimension, not a default

**Context.** Asked what actually motivated the chosen network. The honest answer
is that only part of it was motivated at all.

**Finding.** The three heads are argued for: policy and value are the
actor-critic minimum, and the belief head has a stated three-part justification
(shapes the torso toward the inference channel, gives a cheap diagnostic, makes
play inspectable). The *torso* is not an independent decision — it falls out of
the representation choice in METHODOLOGY §4. Once features are a hand-engineered
flat vector, an MLP is the default consumer of a flat vector. And that
representation choice rests on a single cited ablation from a different rule set
(RLCard), reporting that learned embeddings failed to help where explicit
structure did. Suggestive, not decisive — and §4 is by our own description "the
decision that sets the ceiling".

**Decision.** Phase 4 runs a bake-off rather than assuming: (A) residual MLP over
flat features, (B) set encoder over card embeddings, (C) sequence encoder over
the action history, (D) MLP on the raw 644-dim observation. Equal gradient-step
budget, three seeds each, heads fixed, only the torso varies.

**(D) is the point.** It is the no-features control, and it is the one a plan
like this usually omits. Phase 1's history-necessity gate tests the feature set
with a *probe classifier*; only (D) tests it end-to-end on the real objective.
If (D) is competitive with (A), §4's central premise does not hold in our rule
set — and Phase 4, where a run is minutes, is where we want to learn that.

**Consequence.** `gate-p4` requires the comparison table (paired score with CI,
`belief/auc` on undetermined cards, parameter count, steps/s) and the
equal-budget discipline. It does **not** require a particular winner; whichever
torso wins carries forward with its margin recorded. The trade under the
add-a-metric rule: this adds no evaluation metric, it reuses `gate-p4`'s
existing ones across four arms.

## 2026-09-07 — RL-BR moves to Phase 3, where its answer can be checked

**Context.** Review question: which decisions are mistakes or made too early.

**Finding.** RL-BR was specified only in Phase 5, built alongside the champion it
measures. But RL-BR is itself a training run — undertrained, mistuned or simply
broken all read as *"the champion is hard to exploit"*, and no gate anywhere
validated it. That is the project's headline worst-case number resting on an
unvalidated measurement, in a plan whose whole philosophy is "validate where
truth is computable".

**Decision.** `ginrl/eval/rlbr.py` is built in Phase 3 and gated there: RL-BR
against a fixed uniform-random policy must recover the exact NashConv on Kuhn
(0.9167) and Leduc (4.7472) within tolerance. Phase 5 then *applies* a
calibrated instrument.

**Two smaller fixes recorded with it.** (1) The belief head's Phase 4 baseline
was marginal card frequency, which it can beat by echoing an input feature —
`BeliefTracker` already tells the network which cards the opponent holds.
`belief/auc` is now scored only over cards the tracker has *not* determined,
which is the set where inference actually happens. (2) Phase 7 matched cells on a
fixed reduced budget, which confounds the rule effect with training progress in
the specific direction §6.2 predicts — undertrained agents gin more, so the
curve would partly measure which cells got further. Cells are now matched on
`points_per_hand_vs_anchor` plateauing, and the budget each cell needed is
reported as a result.

**Landmine 12 narrowed.** "The environment is not the bottleneck" was asserted
from a *raw* stepping benchmark that excludes `to_observation_struct().to_dict()`
per seat per decision and `BeliefTracker` accumulation — the pipeline actually
running. The claim now says raw stepping is not the bottleneck and the feature
path is unmeasured until Phase 1 measures it.

## 2026-09-07 — External benchmarks: ISMCTS at budget, and nothing new on the dependency list

**Context.** Asked whether pre-existing bots exist to benchmark against.

**Finding.** Four candidates. `SimpleGinRummyBot` (OpenSpiel) — already the
anchor, and almost certainly a port of `SimpleGinRummyPlayer` from the EAAI
reference implementation, which would make our 0-Elo anchor the field's own
reference player. `pyspiel.ISMCTSBot` — in-process, and the published baseline
used for gin rummy in the 2026 gold-standard study. RLCard's
`gin-rummy-novice-rule` — different rule set, so scores are not comparable, and a
second engine. The EAAI Java field including Heisenbot — a JVM bridge, and the
repository states no licence.

**Decision.** The benchmark ladder is `SimpleGinRummyBot` plus **`ISMCTSBot` at
several pinned search budgets**, treated as distinct ladder members. Budget is a
dial, so this gives a ladder of increasing strength rather than one pass/fail
opponent, and a number against it is comparable to published work. No new
dependency, so no dependency ADR is needed — which is the point.

**Not adopted, with reasons recorded** so this is not re-litigated: RLCard
(incomparable rules, second engine), EAAI Java bots (no licence, JVM bridge).
If an external comparison is ever wanted, the cheap route is that OpenSpiel's
parameters already equal EAAI's — gin 25, undercut 25, knock 10, match to 100 —
so published win rates can be cited rather than their code run.

**To confirm in Phase 2.** Whether `SimpleGinRummyBot` really is the EAAI
`SimpleGinRummyPlayer`. Record the answer either way; if it is, the anchor's
provenance is worth a sentence in the write-up.
